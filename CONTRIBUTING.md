# Как участвовать в VoteFlow

Спасибо, что помогаете. Ниже — правила, по которым живёт репозиторий: окружение, проверки, коммиты, версии и выпуск.

## Окружение

- Node.js 22 или новее
- Chrome или Chromium 105+ для запуска расширения

```bash
npm install   # зависимости и хук commit-msg (git config core.hooksPath .githooks)
npm run check # линтер, целостность, журнал изменений, unit-тесты
```

Расширение загружается как распакованное: `chrome://extensions/` → «Режим разработчика» → «Загрузить распакованное расширение» → корень репозитория. После правок нажмите «Обновить» у расширения.

## Команды

| Команда | Что делает |
|---|---|
| `npm run check` | Всё, что проверяет CI, кроме теста страницы настроек |
| `npm run lint` / `npm run lint:fix` | ESLint |
| `npm test` | Unit-тесты: конфигурации всех сайтов, расчёт времени голосования, `parseCooldown`, миграции, правила коммитов |
| `npm run test:ui` | Тест страницы настроек в headless Chrome |
| `npm run sites` | Проверка доступности сайтов-рейтингов |
| `npm run changelog` | Пересобрать `CHANGELOG.md` из `docs/releases/*.md` |
| `npm run release -- <patch\|minor\|major>` | Подготовить выпуск (см. ниже) |

## Ветки и pull request

- Основная ветка — `refactor`. Работайте в отдельной ветке и откройте pull request в неё
- Один pull request — одно изменение: исправление сайта, новая возможность, переработка
- CI (`.github/workflows/check.yml`) должен быть зелёным
- Исправили ошибку в логике времени, разборе ссылок или таймеров — добавьте тест
- Тексты интерфейса — на русском; новые ключи локализации добавляйте во все языки `_locales/`

## Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): тип и область по-английски, описание по-русски.

```
<тип>(<область>): <что изменилось>

<необязательное тело: почему и как, на русском>

<необязательно: BREAKING CHANGE: что сломается у пользователей>
```

Примеры:

```
fix(mctop.su): отправка голоса после SmartCaptcha
feat(popup): добавление проекта с открытой страницы
fix(captcha): слайдер SmartCaptcha на cloud.yandex.ru
refactor(options): разбить страницу настроек на модули
docs: правила коммитов и версий
release: 9.1.0
```

**Типы**

| Тип | Когда |
|---|---|
| `feat` | Новая возможность или новый сайт |
| `fix` | Исправление ошибки или голосования на сайте |
| `perf` | Ускорение без изменения поведения |
| `refactor` | Переработка кода без изменения поведения |
| `test` | Тесты |
| `docs` | Документация |
| `style` | Оформление кода без изменения логики |
| `build` | Сборка, зависимости |
| `ci` | GitHub Actions |
| `chore` | Прочее обслуживание |
| `revert` | Откат коммита |
| `release` | Выпуск версии — только `release: X.Y.Z` |

**Область** — необязательна. Для сайтов это домен из `projects.js` (`topcraft.club`, `minecraftrating.ru`), для остального — часть расширения: `popup`, `options`, `background`, `captcha`, `db`, `i18n`, `manifest`.

**Правила описания**

- Описание с маленькой буквы, кроме названий (`fix(opera): Opera — кнопки…`), без точки в конце
- Заголовок не длиннее 100 символов, между заголовком и телом — пустая строка
- Несовместимое изменение отмечается `!` после типа (`feat!:`) или строкой `BREAKING CHANGE:` в теле

Хук `commit-msg` проверяет сообщение при каждом коммите, CI — все коммиты в push и pull request. Проверить вручную: `node scripts/commit-msg.js --message "fix: …"`.

## Версии

VoteFlow следует [SemVer](https://semver.org/lang/ru/) — `MAJOR.MINOR.PATCH`. Для расширения это значит:

| Часть | Когда поднимать | Пример |
|---|---|---|
| **MAJOR** | Пользователю нужно что-то сделать руками или он теряет данные: смена ID расширения, несовместимый формат экспорта, удаление возможности | 9.0.0 — собственный ID |
| **MINOR** | Новые возможности, новые сайты, новые разрешения в манифесте | 8.2.0 — уведомление о новой версии |
| **PATCH** | Исправления голосования и ошибок без новых возможностей | 8.3.2 — minecraftrating.ru и McTOP |

- Версия одна на проект: `manifest.json` и `package.json` всегда совпадают (проверяет `npm run check`)
- Тег выпуска — `vX.Y.Z`, он должен совпадать с версией (проверяет workflow выпуска)
- Версия базы данных (`idb.openDB('avr', N)` в `src/core/main.js`) ведётся отдельно и поднимается при каждой новой миграции в `src/utils/database/db-migrations/`. Миграция не должна терять данные пользователя
- Новое разрешение в `manifest.json` — минимум MINOR, и о нём пишется в заметках к выпуску: браузер может попросить пользователя подтвердить доступ

## Выпуск

1. Подготовка:
   ```bash
   npm run release -- patch   # или minor, major, или точная версия 9.1.0
   ```
   Команда поднимает версию в `manifest.json` и `package.json`, создаёт черновик `docs/releases/<версия>.md` из коммитов с прошлого тега и пересобирает `CHANGELOG.md`
2. Перепишите черновик для пользователей: что изменилось для них, а не какие файлы правились. Затем `npm run changelog`
3. `npm run check` и `npm run test:ui`
4. Коммит и тег:
   ```bash
   git add -A && git commit -m "release: 9.1.0"
   git tag -a v9.1.0 -m "VoteFlow 9.1.0"
   git push origin HEAD v9.1.0
   ```
5. GitHub Actions (`release.yml`) сверит тег с версией, соберёт `VoteFlow-<версия>.zip` и опубликует релиз с заметками

Заметки к выпуску (`docs/releases/<версия>.md`) начинаются строкой `<!-- date: ГГГГ-ММ-ДД -->`. Журнал `CHANGELOG.md` собирается из них — правьте заметки, а не журнал.

## Ключ расширения

ID расширения задаётся полем `key` в `manifest.json`. Не меняйте его: у пользователей потеряются данные. Приватный ключ хранится вне репозитория и в git не попадает.

## Новый сайт

Как добавить сайт, описано в [CLAUDE.md](CLAUDE.md#adding-support-for-new-sites): запись в `src/core/projects.js`, скрипт `src/scripts/sites/<домен>.js`, при необходимости — тихий режим. `npm test` проверит разбор ссылки и интервал для нового сайта, `npm run check` — что скрипт существует. Обновите число сайтов в README.
